# Agent 接入层超时排查（2026-09-17）

结论：已复现用户提供的 lexical 请求，主要耗时在 PostgreSQL 正文候选匹配与后续排序链路。默认 15 秒查询预算触发 HTTP 504，CLI 显示 TIMEOUT。该请求不调用 embedding，且本机直连同样失败；网络不是本次复现的主要原因。

以下“复现与基线”至“原始测量产物”为优化前的只读排查记录，当时没有修改服务代码或数据。后续实施结果见末尾“优化实施与验证”。测量受缓存与其他服务负载影响，小样本不能替代持续负载评测。

## 已确认的主要瓶颈

### 1. 宽泛分词与正文大表扫描叠加

`scripts/query/contract.mjs` 的 `tsQuery` 把全部词项按 OR 连接。本机实际将“加息 AI”生成 `'加' | '息' | 'ai'`。匹配单字即可入选，召回范围远大于“同时讨论加息与 AI”的自然语言含义。

正文表统计约 1,359,712 行，包含保留的历史版本，总空间约 5,491 MB；GIN 全文索引约 605 MB。当前先在正文表匹配，再通过 document_id/revision_id 限定当前版本，历史版本也增加底层检索成本。

原始执行计划选择遍历 documents，再通过 blocks 主键读取各文档版本并判断全文条件，没有在这个分支直接使用 GIN。计划对正文分支仅估计约 10 条结果；另一个保持查询语义的哈希连接试验实际得到约 86,547 条正文候选，说明相关行数估计偏差很大。

哈希连接试验虽然使用 GIN，仍需约 36.6 秒：GIN 找到 171,456 条正文记录，当前版本连接后加上元数据候选共 92,547 条，再从中选择 120 份材料、每份最多 3 条候选。其 PostgreSQL shared read 约 240,273 个 8 KiB 缓冲块，约 1.83 GiB；这是数据库缓存外读取量，不能直接等同于物理磁盘读取量。

因此，“加索引”或“强制使用现有 GIN”都不能单独解决问题。另一个物化匹配块的试验也触发超时；去除正文评分、去除正文 ILIKE 加分的两种试验仍超过 20 秒，说明匹配及记录读取本身已经很重。

### 2. limit 只约束最终输出，不能降低前置工作量

`scripts/query/service.mjs` 的 search 固定使用 120 个文档候选，deep 使用 300 个；`--limit 8` 在最后的内存分页才生效。候选选出前仍需对所有匹配记录计算排序。

query 通过 `listDocuments(limit:100001)` 先加载所有符合条件的文档及元数据，在 Node 中生成并保存快照，再分页。当前无筛选查询读取约 15,765 份材料；单独测量全量取数约 6.3 秒，HTTP 首屏约 5.5 秒。每份材料还执行实体 ID 关联聚合。

read 的 metadata、outline、blocks 三种视图也都会先加载指定版本的全部正文块。hybrid 的向量证据补全会加载候选文档的全部正文块。这两项是代码确认的放大量，本次未独立量化其耗时。

### 3. 超时发生在服务查询预算内

- service 默认预算为 15,000 ms；SQL 设置 statement_timeout，并监听取消信号。
- CLI 默认等待查询预算再加 3,000 ms。
- HTTP server.requestTimeout=130,000 ms 主要约束请求接收，不能覆盖业务查询的 15 秒预算。
- HTTP 504 的错误正文被统一替换为“研究服务暂时不可用”，但 code 保留 TIMEOUT；当前 Agent HTTP 入口也没有慢请求阶段日志。

所以只调高 HTTP requestTimeout 没有效果；提高业务超时能延后报错，但不会降低查询成本或改善并发。

## 会放大问题的因素

以下来自代码或配置检查，不应当作已经完成并发压测的结论：

- Agent 默认允许 8 个并发请求，数据库共享池只有 4 个连接。Wiki 与后台索引也使用此池；索引会保留一个连接持有锁，并另外使用事务连接。慢查询可能阻塞本应很快的请求。
- 取消处理安装在获得事务连接后的查询上；连接池排队阶段没有独立的取消/排队截止机制。
- hybrid 顺序执行 coverage、lexical、证据补全，再进行最长 8 秒的 embedding 和精确向量扫描，最后还有证据补全。lexical 已用去 8–12 秒时，剩余预算很紧。
- vectorCandidates 对过滤集合做精确向量排序，不是 ANN；宽泛搜索的成本随块数增加。
- 每个请求都计算 coverage；本次一次单独测量约 1.3 秒。实体过滤还会追加图索引覆盖检查。
- PostgreSQL shared_buffers=128 MB、work_mem=4 MB。相较正文与索引体积，缓存偏小；执行计划出现约 6 MB 排序落盘。但该试验主要时间仍在候选扫描阶段，不能把排序内存视作唯一原因。调整前需核实数据库容器内存限制。

最初活动快照仅见其他连接 idle、没有锁等待；后续检查也没有残留诊断查询，因此没有证据把本次超时归因于持续锁阻塞。

## 建议修复顺序与验收

1. **先修 lexical 查询计划与召回语义。** 明确多词查询的词组、AND/OR 规则，避免中文单字 OR 意外扩大召回；作为公开契约变更处理，不能悄悄用 AND 换取速度。分离当前版本的轻量全文检索投影和历史证据存储，先做受过滤条件约束的候选检索，最后读取少量正文证据。若采用有上限的候选阶段，需要明确暴露截断/召回覆盖，验证排序质量。
2. **把分页与字段裁剪下推。** query 按所需字段返回，用有稳定版本语义的分页方案替代完整元数据快照；不能简单改为 OFFSET 而破坏现有游标一致性。read 按视图/page/block 选取必要数据。向量补证也应避免拉取所有候选的全部正文。
3. **给检索与索引分配独立资源预算。** 隔离连接池与后台索引，给连接排队设置取消和期限；按数据库承载能力设置准入，不能只扩大池和并发数。加入各阶段耗时、排队耗时与超时阶段日志，不记录 token 或全文。
4. **优化 hybrid 并验证数据库容量。** 为 lexical、embedding、vector 和证据补全分配阶段预算，保证可用的 lexical 结果能及时降级返回。在不破坏条件内召回的前提下评估 ANN。结合容器内存和缓存命中率再调整 PostgreSQL 参数。

建议目标：以本次原始命令为必测用例，覆盖无筛选、标签、实体条件及宽泛词；单请求 lexical 常用样本目标低于 3 秒，8 并发下目标 p95 低于 5 秒且无默认预算超时。这些是待实现、待压测的验收目标，并非本次已达到的性能。

另外，索引状态记录有 2 份材料 Unicode 转义失败，导致 coverage 标为 incomplete。这应另行修复，但不是本次 SQL 扫描超时的直接解释。

## 优化实施与验证

已实现当前版本文档级词项投影、GIN 词项召回与文档内片段排序。标题匹配和元数据全文匹配拆为独立分支，避免跨列 OR 导致扫描全部向量。查询事务仅在这条 SQL 内关闭顺序扫描偏好及 JIT，完成后恢复；没有改动数据库全局参数。原有 OR 匹配及筛选条件保留，候选截断发生在筛选后，并明确返回策略与截断标记。排序改为文档优先，不能声称与旧排序完全等价或相关性指标已经提升。

query 改为固定版本的轻量快照加按页读取元数据；read 的 metadata/outline 避免拉取正文和全文向量；向量补证仅传输可匹配的块。新增独立研究读取连接池、可取消的 FIFO 排队、5 秒可选语义阶段预算和不包含凭据/查询内容的慢请求日志。目录状态和发布日期增加派生标量列，减少反复解压元数据。
